# Factory adoption readiness

[Delivery lifecycle](factory-delivery-lifecycle.md) · [Project binding](factory-project-binding.md)

## Purpose and trigger

Use when first adopting a set of controls and guides or changing their relationships, operating assumptions, or local bindings. The source separates portable documentation readiness from product implementation and operational qualification.[^readiness] Its original whole-folder copying mechanism is adapted here to selecting individually pinned catalog concepts.[^readme]

## Inputs and owner

The adoption owner assembles selected concept identities and exact catalog URLs, required dependencies, the local project binding, actual grants, and existing evidence. Use the [catalog adoption procedure](../adoption.md) for copied content and local adaptations.

## Procedure and evidence

| Review | Evidence to retain | Failure disposition |
|---|---|---|
| Selection and references | All selected nodes and needed dependencies are accessible in the intended distribution; relative links and source pins resolve. | Repair missing dependencies before claiming a usable adoption. |
| Project separation | Binding uses this project's intent, grants, paths, and constraints; generic requirements contain no copied host authority. | Correct inherited assumptions; leave unknowns explicit. |
| Normal lifecycle | One request traced through [delivery lifecycle](factory-delivery-lifecycle.md), naming each owner and exit observation. | Repair missing handoffs or acceptance criteria. |
| Failure lifecycle | Walk failed checks, interruption, conflicting edits, denied access, and ambiguous release/recovery. | Reject routes that bypass a gate, repeat an unknown mutation, lose work, or falsely report completion. |
| Coordination, if selected | Walk independent contributions, shared limits, failed integration, and obsolete writers. | Record capability gaps and select serial work or block the dependent arrangement. |
| Dispatcher, if selected | Walk each return state, missing packet, interruption, and exhausted allowance under the [dispatcher guide](factory-dispatcher-handoff.md). | No additional writer until predecessor ownership is safe; no fabricated successful return. |
| Portability | Bind a second unrelated project without changing generic rules or reusing its grants. | Separate project assumptions from reusable controls. |
| Quality | Walk a missing required tool, diagnostic warning, unexplained skip, and injected defect. | The affected acceptance stays blocked; a formatter run is insufficient. |
| Document-only scope | Trace a guide that mentions restore, rotation, or browser tests. | Complete the document without inventing services or executing those actions. |

Record scope, actual observations, gaps, owner, and disposition in the adopter's evidence. Reopen affected review when instructions, references, or assumptions change.

## Readiness claims

Keep separate findings for definition usability, local implementation, and observed operational outcomes. A paper exercise may support the first only. If the user explicitly requires factory qualification before product work, preserve that dependency; identify missing runtime evidence without pretending the walkthrough supplied it. Unknown commands, accounts, and measurements remain unknown.

This guide is an adoption procedure; the actual selected controls provide their own pass/fail assessments. No trial has been performed for these proposed nodes.
